# 内部交付协作平台（worklist / workRecord）系统计划书

> 版本：v1（基于 2026-08-23 现状整理）
> 范围：把当前"个人自用需求记录 + 运维平台构建转发"升级为"多角色协作的交付管控平台"
> 关联文档：`devops-delivery-platform-plan.md`（前期产品方案，本文为其落地与扩展版）

---

## 0. 现状盘点（已经做了什么）

| 仓库 | 现状 | 说明 |
|---|---|---|
| `workRecord`（前端） | ✅ 可用 | React18 + Vite + Ant Design5；需求登记/编辑、状态流转、发版时间、大版/独立版本、筛选、统计、导出/导入、运维平台构建按钮（`src/build.ts`） |
| `worklist-serve`（后端） | ✅ 可用 | Koa2 反向代理，把 `/devops-api/*` 转发到 `devops.vzan.com`（构建/分支/应用接口），托管前端 dist |
| 数据层 | ⚠️ 仅 localStorage | 需求数据在浏览器本地，无后端持久化、无用户体系、无协作能力 |
| 提测→构建 | ✅ 手动 | 需求里登记开发分支后，人工在页面点"构建"触发运维平台 |

**已验证能力**：可提交 MR、可自动构建（运维平台）、可记录大版需求。
**还缺的能力**（即本计划要补的）：多角色、权限管理、子开发人员/前后端分支、操作记录、AI 报告链路、知识沉淀。

---

## 1. 系统要解决的问题

### 1.1 当前痛点
1. **信息孤岛 + 手工串联**：GitLab（代码）、TAPD（需求）、运维平台（构建）三套系统靠"传话筒"式人工串联，状态不透明、易错、难追溯。
2. **记录是个人私有，不是团队资产**：localStorage 数据只在自己浏览器，换人或换设备即丢失，无法多人协作与审计。
3. **没有角色与权限**：当前"添加需求"只是自用形态，无法区分产品/开发/测试职责，也无法控制谁能提交、谁能同意提测、谁能指派。
4. **一个需求只有"开发"视角**：无法细化到前端/后端各自的项目与开发分支，合并与构建时责任不清。
5. **流程无操作留痕**：谁在何时把状态从 A 改成 B、为什么改，全部靠口头，复盘困难。
6. **测试/开发价值靠人肉**：提测后代码 review、影响范围评估、Bug 复盘、知识沉淀都靠人工，慢且不稳定。

### 1.2 本系统定位
一个**内部 DevOps 交付编排 + 协作平台**：从需求录入开始，串联 GitLab MR、运维平台构建/部署、TAPD 状态；用统一状态机作为唯一真理源，关键环节保留人工审批；并接入 AI 在提测/测试通过/发布三个节点自动产出报告。

> 版本回退、环境重置等高风险操作**不**在本系统做，仍走旧运维平台（已确认）。

---

## 2. 目标效果（做完后什么样）

| 角色 | 用系统前 | 用系统后 |
|---|---|---|
| 产品 | 口头/文档提需求 | 在平台确认需求归属，指派开发与测试 |
| 开发 | 手动建 MR、手动构建、手动改 TAPD | 录入需求+前端/后端分支→点提交，系统自动建 MR、改 TAPD、触发构建 |
| 测试 | 追着开发问"编好没" | 平台一键同意提测，实时看"合并中→构建中→部署中→就绪" |
| 领导 | 去 GitLab 点 Merge、留痕散落 | 在平台点"同意"，操作全部留痕、权限收敛 |
| 全员 | 复盘靠记忆 | 每单有完整操作记录 + AI 报告 + 知识沉淀 |

**量化预期**（内部工具，定性为主）：提测到测试环境就绪的人工点击从 ~5 次降到 1 次；状态争议/追问基本归零；每轮需求自动生成 3 类 AI 报告，复盘成本大幅下降。

## 3. 整体架构

```
┌────────────────────────────────────────────────────────────┐
│ 前端 workRecord (React+antd)  —— 多角色视图、需求、构建、报告 │
└───────────────┬────────────────────────────────────────────┘
                │  HTTP / JSON
┌───────────────▼────────────────────────────────────────────┐
│ 后端 worklist-serve (Koa2 → 升级为带持久化+权限+任务)        │
│  · 反向代理 /devops-api/* → 运维平台（保留）                  │
│  · 新增：需求 CRUD、用户/角色、权限、操作日志、MR/构建编排     │
│  · 新增：AI 报告生成任务（调 AI 服务）                        │
│  · 持久化：引入数据库（SQLite 起步 / Postgres 可选）          │
└───┬───────────┬──────────────┬──────────────┬───────────────┘
    │           │              │              │
 GitLab API  TAPD API   运维平台 API      AI 服务(代码review/影响范围/质量/沉淀)
    │           │              │
   MR/commit  需求状态变更   构建/部署任务
```

**登录**：复用运维平台账号体系（OAuth/SSO 或 cookie 透传方案延续），首次登录自动建档。

## 4. 数据模型升级（localStorage → 后端库）

在现有 `Requirement`（需求名、TAPD、项目分支、状态、发版时间、版本、备注）基础上扩展：

```sql
-- 用户与角色（多对多，一人可多角色）
users(id, ops_account, name, email)
user_roles(user_id, role)  -- dev_lead/test_lead/product_lead/developer/tester/admin

-- 需求单（原 Requirement 上云）
requirements(
  id, name, tapd_url, version, status, release_date, remark,
  product_lead_id,         -- 需求归属（产品指派）
  created_by, created_at, updated_at
)

-- 子开发：一个需求拆前端/后端，各自项目+分支
sub_devs(
  id, requirement_id,
  type,                    -- frontend / backend
  owner_id,                -- 指派的具体开发
  project, branch,
  baseline_commit_id,      -- 提交提测时锁定，用于冲突预检
  mr_id, build_id, env_url -- 编排过程产物
)

-- 操作记录（审计，必做）
operation_logs(
  id, requirement_id, operator_id, action,
  from_status, to_status, remark, created_at
)

-- AI 报告（未来拓展）
ai_reports(
  id, requirement_id, type,   -- code_review / impact / quality / knowledge
  audience,                   -- developer / tester
  content, status,            -- pending/ready/confirmed
  created_at
)
```

## 5. 分阶段实施计划

### Phase 0 —— 上云与协作底座（必须先做）
> 多角色/协作的前提是数据不再在 localStorage。

- [ ] 后端引入数据库（推荐 SQLite 起步，零运维；后续可换 Postgres）
- [ ] 需求 CRUD 改为后端 API + 前端走接口（保留 localStorage 作为离线兜底/导入）
- [ ] 用户体系：运维平台账号登录建档、`users` / `user_roles` 表
- [ ] 角色管理页：领导给成员分配角色（产品/开发/测试/各 lead/admin）
- [ ] 权限中间件：按角色控制接口可见性与可执行动作
- [ ] 操作记录：所有状态扭转/指派/强制扭转落 `operation_logs`，前端可查看时间线

**效果**：从"我自己的记事本"变成"团队可协作、可审计的协作台"。

### Phase 1 —— 止血期：提测→测试环境自动化（沿用前期方案）
- [ ] 需求下挂"子开发"：前端、后端各自项目+分支，分别指派 owner
- [ ] 提交提测：锁定各分支 `baseline_commit_id`，调 TAPD 改"已提测"
- [ ] 测试"同意提测"：冲突预检（模拟 MR）→ 自动建 MR 并合并 → 调运维平台构建 test 分支 → 部署 → 探活 → 置就绪
- [ ] 进度可视化：合并中/构建中/部署中/就绪 进度条
- [ ] 强制扭转状态后门（仅改本地 + 写日志，回退去旧平台）
- [ ] 钉钉通知：冲突@开发、就绪@测试、失败@开发+测试

**效果**：提测到测试环境就绪全自动，开发只等通知。

### Phase 2 —— 规范期：预发布/发布 + 权限收敛
- [ ] 预发布/生产 MR 强制走本系统发起，领导在平台点"同意"即由服务账号完成合并
- [ ] 大版发布日历、待发布聚合、一键构建线上制品（不发布）+ 双确认（开发领导+测试领导）
- [ ] 需求归属/开发/测试指派由对应 lead 在平台完成，数据权威

**效果**：操作全部留痕、权限收敛到角色，不再依赖 GitLab 手动点。

### Phase 3 —— 智能化：AI 报告链路（你的未来拓展）
见第 6 节。

### Phase 4 —— 知识化：发布后沉淀
见第 7 节。

## 6. 未来拓展 A：AI 报告链路（按节点自动产出）

触发链路由"提测 / 测试通过 / 发布"三个状态节点驱动，调用 AI 服务（接入 DeepSeek 等），产出 4 类报告：

### 6.1 提测后（开发点提测触发）
1. **AI 代码 Review 报告（给开发看）**
   - 输入：本次 MR 的 diff / commit
   - 产出：潜在 bug、风格/规范、性能/安全、改进建议，按严重级别排序
   - 价值：把 review 提前到提测即发生，开发及时改，减少测试轮次
2. **AI 影响范围报告（给测试看）**
   - 输入：变更文件 + 调用链路 + 历史测试点
   - 产出：受影响模块、建议重点回归范围、风险点
   - 价值：测试不再盲测，精准圈定回归用例

### 6.2 测试通过后（测试点"通过"触发）
3. **AI 质量归档报告（总评）**
   - 输入：本轮需求提的 Bug 列表 + 代码 review 结论 + 影响范围 + 通过情况
   - 产出：本轮质量评分/总评、主要风险、遗留问题、责任建议
   - 价值：每次需求一份质量结案，便于复盘与考核依据

### 6.3 实现要点
- 报告异步生成（不阻塞提测/发布主流程），状态 `pending → ready` 后通知对应角色
- 报告存 `ai_reports`，与需求单关联，可在需求详情页查看
- AI 服务以可插拔适配器封装，模型可替换

## 7. 未来拓展 B：发布后知识沉淀报告

触发：需求状态到"已发布"后系统自动生成。

- [ ] **知识沉淀报告**：综合代码 review 结论、影响范围、质量归档、本轮 Bug 归因
- [ ] 拆成两份视角：**测试知识**（易错点、回归策略、典型缺陷）与 **开发知识**（设计缺陷、最佳实践、踩坑）
- [ ] 各自推送给对应角色**确认**：测试确认哪些"可靠"的沉淀到测试知识库，开发确认哪些沉淀到开发知识库
- [ ] 确认后的条目进入知识库（独立存储 `knowledge_base`），供后续需求 AI 报告检索引用（形成正循环）

**效果**：每次发布都在"攒组织资产"，AI 报告越用越准。

## 8. 明确不做（边界）

- ❌ 版本回退 / 环境重置按钮（回退走旧运维平台）
- ❌ 需求独立环境（仅预留字段）
- ❌ 多需求打包合并（一次构建一条 test 分支）
- ❌ 脱离运维平台账号体系自建登录（复用现有）

---

## 9. 风险与应对（沿用前期结论）

| 风险 | 应对 |
|---|---|
| 自动合并冲突卡死 | 走 MR API + 冲突预检，冲突硬拦截并强提醒开发 |
| 三系统状态不一致 | 本地 DB 为唯一真理源，外部调用幂等 + 异步确认 |
| 领导还要去 GitLab 点 Merge | 系统用服务账号 Token，平台点"同意"即完成，留痕在本系统 |
| 多需求并发构建时光倒流 | 构建只传分支名 `test`，不锁 Commit（仅 baseline 用于预检/回退参考） |
| AI 报告拖慢主流程 | 全异步生成，主流程不阻塞 |

---

## 10. 总结：解决什么 / 效果如何（一句话版）

> 本系统把"需求登记 → 提测 → 构建部署 → 测试 → 发布"的全链路从三套散系统的人工串联，收敛为一个带**角色权限、操作留痕、子开发拆分**的协作平台；并以**AI 报告（代码 review / 影响范围 / 质量归档）**和**发布后知识沉淀**把每轮需求的人工复盘成本转化为可累积的组织资产。最终效果：开发少点、测试少问、领导留痕、复盘有凭、知识越用越厚。
