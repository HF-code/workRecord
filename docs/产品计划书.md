# 内部交付协作平台 产品计划书


> 目标：把"需求到上线"的全流程，从三套系统的人工传话筒，升级为一个**带角色权限、全程留痕、能自动跑、还能自我沉淀**的协作平台——让开发少点、测试少问、管理留痕、经验留得下来。

> 思路：先自动化 再智能化

---

## 一、为什么要做这件事（背景与问题）

我们日常的交付流程，从"需求提出"到"上线发布"，要横跨 **三个系统**：

- **GitLab**（写代码、提合并请求）
- **TAPD**（记录需求、跟踪状态）
- **内部运维平台**（构建、部署测试/预发布/生产环境）

目前这三套系统是**靠人工手动串联**的。一个需求从开发写完到测试能在测试环境验证，中间存在大量"传话"和"重复点击"：

1. 开发手动合并代码 → 手动去运维平台点构建 → 测试再手动发布；
2. 测试通过后，又要等通知、再手动提合并请求、等有权限的人去点合并、再手动构建预发布；
3. 上线时，再次依赖多人手动操作与口头协调。

**由此带来三个核心问题：**

| 问题 | 表现 | 后果 |
|---|---|---|
| **效率低** | 大量重复点击与等待通知，一个需求要人工操作 5 次以上 | 开发测试时间被琐碎操作消耗 |
| **大版统计靠人肉** | 大版有哪些需求要发，全靠测试自己记录、大版日发通知；开发也全靠自己记忆"哪些是我的、含哪些项目哪些分支" | 大版日全员要"谨慎回忆"，极易漏发、错发 |
| **无沉淀** | 代码 review、影响范围、质量复盘全靠人脑记忆 | 同样的问题反复踩，组织经验留不下来 |

> 说明：需求进度本身一般都会自觉改 TAPD，状态"看得到"不是主要矛盾；真正的痛点在于**大版聚合统计**和**开发侧归属/分支记忆**全靠人工，以及缺少角色区分带来的职责不清。

---

## 二、我们要做成什么样（产品目标）

我们要建一个**内部交付协作平台**，把"需求 → 提测 → 构建部署 → 测试 → 发布 → 沉淀"的全流程，从三套散系统的人工串联，收敛成**一个统一、透明、可协作、可审计**的平台。

### 2.1 核心能力（做成一个闭环）

**1）统一需求与协作台**
- 需求在平台统一登记，支持大版/独立版本管理；
- 一个需求可由**多名开发参与**，每人自行填写自己负责的项目与开发分支（前端、后端或其他，不限数量）；
- 产品、开发、测试在各自视角看到与自己相关的需求，状态一目了然。

**2）多角色与权限管理**
- 系统区分 **产品、开发、测试** 三类角色，以及各方向的负责人（如开发负责人、测试负责人）；
- 不同角色拥有不同操作权限：谁能提交提测、谁能发布到测试环境、谁能指派、**管理者**拥有上线审批权，由权限收敛。

**3）提测到测试环境：自动化串联**
- 开发在平台点"提交提测" → 系统自动创建合并请求、自动触发运维平台**构建制品**（注意：仅构建，不发布）；
- 测试在平台看到已构建好的制品，点"发布"即部署到测试环境开始测试；
- 冲突或构建失败自动提醒对应开发，无需测试追着问"编好没"。

**4）全流程操作留痕**
- 每一次状态扭转、每一次指派、每一次审批，系统**自动记录"谁、在何时、从什么状态改到什么状态、为什么"**；
- 任何一笔需求都可回溯完整时间线，管理和复盘有据可查。

**5）发布审批门禁**
- 预发布、大版上线等关键动作，必须由**管理者**在平台**审批确认**后，系统才执行；
- 操作集中在平台完成并留痕，减少"私下点合并"带来的失控风险。

### 2.2 智能化与知识化（远期规划，分两阶段）

在基础闭环跑通后，引入 AI 在关键节点自动产出报告，把"人肉复盘"变成"系统自动生成"：

**阶段一：提测与测试期间**
- **AI 代码 Review 报告（给开发）**：提测即自动对本次变更做代码审查，提前暴露问题，减少测试轮次；
- **AI 影响范围报告（给测试）**：自动分析变更波及的模块，给出重点回归建议，让测试不再"盲测"。

**阶段二：测试通过 / 发布后**
- **AI 质量归档报告**：综合本轮 Bug、review 结论、影响范围，给出本轮质量总评，作为复盘与考核依据；
- **AI 知识沉淀报告**：发布后自动生成"测试知识 / 开发知识"两份视角，经对应角色确认可靠项后，**沉淀进团队知识库**，供后续需求复用——让系统越用越"聪明"。

## 三、能带来什么价值（预期效果）

| 角色 | 现在 | 做完之后 |
|---|---|---|
| **开发** | 手工合并、手工构建、靠记忆记自己有哪些需求/分支 | 各自填项目分支，点提交即自动 MR + 构建，归属系统可查 |
| **测试** | 自己记大版要发哪些需求、追着开发问进度 | 平台看已构建制品，点"发布"即开测；大版清单系统自动生成 |
| **产品** | 需求散落在各处、进度靠问 | 平台统一登记、按版本聚合、状态透明 |
| **管理者** | 操作无留痕、合并靠私下协调 | 全流程可审计、关键发布有审批门禁 |

**量化预期（内部工具，以提效定性为主）：**
- 单需求人工操作从约 5 次降至约 1 次；
- 提测到测试环境就绪的等待与追问基本归零；
- 每轮需求自动生成 3 类 AI 报告，复盘成本大幅下降；
- 组织经验从"人脑记忆"转为"可累积、可检索"的知识资产。

---

## 四、边界与原则（明确不做什么）

为避免范围失控，以下明确**不在本期范围内**：

- **版本回退、环境重置**等高风险操作，仍走现有运维平台处理（本系统只做状态记录与编排，不做破坏性操作）；
- 不重复建设需求管理系统，TAPD 继续作为需求源头，本平台做串联与编排；
- 复用现有运维平台账号体系，不自建一套登录。

## 五、推进节奏（建议）

| 阶段 | 内容 | 目标 |
|---|---|---|
| **第一阶段：协作底座** | 需求上云、多角色与权限、操作留痕 | 从"个人记事本"变成"团队可协作、可审计的协作台" |
| **第二阶段：提测自动化** | 子开发拆分、提测→构建部署自动串联 | 解决提测到测试环境的最大痛点 |
| **第三阶段：发布规范** | 预发布/大版发布审批门禁 | 操作收敛、权限可控 |
| **第四阶段：AI 智能化** | 代码 review / 影响范围 / 质量报告 | 把人肉复盘转为自动产出 |
| **第五阶段：知识沉淀** | 发布后知识报告与确认入库 | 形成组织资产正循环 |
